Turning a terminal into a rendering engine — and then building an editor on it.

Addressable cells, layers, styles, diffing, input parsing and a 60 fps loop — 5 111 lines of library, 2 931 lines of editor, 507 tests, zero dependencies. This page explains how all of it works, module by module, with frames captured from the running code.

01 — the idea

Your terminal is a rendering engine

A terminal is normally a stream: you print, the cursor moves on, and you can never take anything back. termrender turns it into a surface — a grid of cells you can address by x,y, write to, restyle, erase, layer, diff and repaint, at 60 frames a second, in pure Python with zero dependencies.

Everything you see below is real: the frames were captured by running this library headlessly while this page was generated, and the code blocks are coloured by tred's own syntax highlighter — the editor built on top of the engine, described in the second half of the page.

The whole API in one sentence: you draw into a Screen, the screen diffs what you drew against what the terminal currently shows, and writes only the difference as ANSI escapes.

Thirty seconds of it

from termrender import Screen, Config
 
screen = Screen(Config(alt_screen=True, mouse=True))
screen.start()
 
greet = screen.put(4, 2, "hello", fg="#4ec9b0", bold=True, id="greet")   # returns a handle
screen.rect(2, 1, 24, 5, "cyan", title="box")                            # raw drawing
greet.move(4, 3)                                                         # relocate the object
greet.style_with(fg="red")                                               # restyle it in place
screen.erase(10, 3, 4, 1)                                                # take raw cells back
screen.remove("greet")                                                   # ...or an object, by id
screen.set_cursor(4, 3)
screen.draw()                                                            # one write, minimal bytes
 
screen.stop()                                                     # terminal restored exactly

That draw() is the heart of it. It composites every layer into a back buffer, compares that with the front buffer (what the terminal is currently displaying), coalesces the differences into runs, and emits the shortest escape sequence that transforms one into the other. Move one label on a 200×60 screen and it writes 37 bytes.

Two drawing models, one buffer

objects — put / move / restyle / remove

Every put() registers a TextObject with an id and a handle. You can move it, restyle it, hide it or remove it later without redrawing anything else. This is the “locate, put and remove text via x and y” model.

paint — raw cells

paint(), fill(), rect(), line(), paint_runs() write straight into the layer's cell grid and register nothing. Cheaper, no bookkeeping, erased by rectangle. tred draws its whole viewport this way.

Everything accepts a style, in five different spellings

All five funnel through one function, normalize_style(). It is the single hottest call in the library, which is why it has a fast path: a Style instance is already normalised by its __post_init__, so it is returned as-is.

03 — submodules

The module map

Fourteen modules, 5 111 lines, no third-party runtime dependency. The dependency graph is a strict stack — cell → text → style → buffer → layer/objects → screen → app — so you can read it bottom-up and nothing above surprises you.

04 — data model

Cells, buffers, styles, layers

Cell — the atom

A cell is (char, style) and nothing else. Cells are interned: drawing the same styled character a thousand times returns the same object a thousand times, which makes the diff loop a pointer comparison instead of a field-by-field equality test.

from termrender import cell, EMPTY_CELL, BLANK_CELL, Style
 
a = cell("x", Style(fg="red"))
b = cell("x", Style(fg="red"))
assert a is b            # interned, identity-comparable
 
EMPTY_CELL.char          # "\x00" — nothing drawn here (transparent)
BLANK_CELL.char          # " "    — a real space was drawn here (opaque)

Three sentinels that do all the heavy lifting

sentinelmeanswhy it matters
EMPTYnothing was ever drawn into this cellThe only transparent value. Layers composite over it; runs of EMPTY at the end of a row collapse into a single CLEAR_TO_EOL.
BLANKa space was drawn here on purposeNot skippable! A blank cell must overwrite whatever the terminal still shows, otherwise erasing text leaves ghosts.
CONTINUATIONthe right half of a double-width glyphLets erase() and put() repair a wide character that got half-overwritten, instead of leaving the terminal showing half a 漢.

Buffer — the grid

A flat list of width × height cells with a coordinate API on top. It knows about tabs, newlines, wrapping, clipping, wide glyphs, combining marks and scrolling. Everything you can do to a screen you can do to a bare Buffer, which is why the test suite can assert on pixels without a terminal.

from termrender import Buffer, Style
from termrender.text import text_width
 
buf = Buffer(20, 4)
buf.put(2, 1, "hello 世界", Style(fg="#4ec9b0"))
buf.row_text(1)                  # '  hello 世界'   — 10 characters
text_width(buf.row_text(1))      # 12 cells — each CJK glyph occupies two
buf.erase(7, 1, 2, 1)            # clips 世 in half...
buf.row_text(1)                  # '  hello   界'   — ...and repairs the orphan
buf.scroll(lines=1)              # the whole grid moves, bottom row clears

Style and Color — cascading appearance

Twelve optional attributes, every one defaulting to “terminal default”, so an empty Style() costs zero escape codes. merge() layers one style over another (that is how inheritance works); diff() emits only the SGR codes needed to get from the previous style to this one.

from termrender import Style, Color, ColorDepth
 
s = Style(fg="#4ec9b0", bold=True)
s.merge(Style(bg="blue"))            # fg+bold kept, bg added
s.diff(Style(bold=True), ColorDepth.TRUECOLOR)   # only the colour code
Color.parse("205").downsample(ColorDepth.BASIC)  # 256-palette → 16 colours
Gotcha worth knowing: merge() can only add — it cannot unset an inherited flag, because “False” and “not specified” are the same value. Use style.with_(bold=False) when you mean it.

Layer — composable surfaces

A layer has its own paint buffer and its own object list, plus z, offset, clip and visible. Composition is painter's algorithm by z, and only EMPTY cells let the layer below show through — which is what makes a translucent HUD or a modal dialog possible without a compositing engine.

screen.layer("hud", z=10)
screen.layer("modal", z=20, visible=False)
 
screen.put(2, 2, "score 10", layer="hud")
screen.get_layer("modal").visible = True     # property → marks the screen dirty
screen.get_layer("modal").offset = (4, 4)    # move the whole layer, contents untouched

Screen — the thing you hold

Screen keeps two buffers of the same size. You draw into the back; the front records what the terminal currently displays. After every draw() they swap. That pair is the entire trick — everything else is bookkeeping.

05 — frame pipeline

What happens inside draw()

One draw() call walks seven stages. The design goal of each is the same: do work proportional to what changed, never to the size of the screen.

  1. You draw

    Every mutating call writes into a layer — either its object list (put) or its raw cell grid (paint). Both set the layer's dirty flag.

    cost: one list append or one slice write

  2. Dirty propagates

    A dirty layer marks the screen dirty. Changing z, visible or offset also re-sorts the layer stack, because those are properties, not fields.

    cost: a bool, plus a sort only when z-order actually changed

  3. Bake objects

    Each dirty layer flattens its TextObjects into its paint buffer, in insertion order, so objects and raw paint can coexist. Raw cells are laid down first.

    cost: proportional to what changed, not to the screen

  4. Composite

    Layers are painted onto the back buffer in z order. Only EMPTY cells are skipped, so a layer can deliberately blank out what is underneath it.

    cost: O(visible cells) — one pass, slice-copied per row

  5. Diff

    Back buffer is compared against the front buffer cell by cell. Unchanged cells are ignored; changed cells are grouped into contiguous same-row runs.

    cost: one pointer comparison per cell (cells are interned)

  6. Emit escapes

    Each run becomes CUP + the minimal SGR delta + the text. A run that reaches the right edge with trailing blanks collapses to CLEAR_TO_EOL. Styles are carried across runs and across frames, so nothing is re-sent needlessly.

    cost: string building — typically tens of bytes

  7. Write, then swap

    The payload is wrapped in ?2026 (synchronised output) if the terminal supports it, written in one call, and only then do the buffers swap, so a failed write can never desynchronise the model.

    cost: one write() syscall per frame

The invariant the test suite enforces

After every draw, the front buffer must equal a from-scratch composite of all layers. If those two ever disagree, the model has drifted from the terminal and every subsequent frame would be wrong. So tests/test_engine.py asserts exactly that, after a scripted sequence of paints, erasures, layer toggles and resizes:

# tests/test_engine.py, verbatim: after every draw, front == composite(layers)
screen = Screen(Config(width=12, height=3, output=out, alt_screen=False, sync_output=False))
screen.start()
expected = Buffer(*screen.size)
for i in range(12):
    screen.put(i % 8, 1, f"v{i}", fg=i % 3, id="v")
    screen.erase(0, 2, 12, 1)
    screen.paint(i % 10, 0, "#")
    screen.draw()                            # the incremental path
    screen._composite_into(expected)         # a from-scratch composite
    assert screen._front == expected         # they must be identical
First frame and diff=False take a different path: a row-wise full repaint. Same output, no comparison — that is what makes frame() usable for headless capture and testing.

Depth is a ceiling, not a choice per call

Config.color_depth defaults to AUTO, which sniffs TERM, COLORTERM and a few known emulators. Every escape the engine emits is downsampled to that ceiling at write time, so your code can speak truecolor everywhere and still look right on an 8-colour terminal. Force it for tests:

Config(color_depth="none").resolved_depth()      # ColorDepth.NONE — no SGR at all
Screen(Config(color_depth="truecolor", quiet=True)).frame_ansi()

07 — hard problems

What makes a terminal hard to drive

Nine things about terminals that will bite you if you treat them like a canvas. Each of these is a piece of the engine, not a caveat in the docs.

double-width characters

A CJK glyph is one character but two cells. If you index by character you will overwrite the wrong thing; if you index by cell you can split a glyph in half and leave the terminal showing garbage. termrender stores cells, marks the right half CONTINUATION, and repairs the neighbour on every overwrite or erase. tred keeps both: Pos.col is a character index, and cell columns are derived on demand.

removal is not “draw nothing”

Erasing a cell has to write something, because the terminal still shows the old glyph. But writing a space is also wrong — it makes the cell opaque and hides the layer below. Hence two distinct values: EMPTY (never drawn, transparent) and BLANK (a real space, opaque).

SGR state is sticky

Terminal attributes persist until reset. Emitting a full style for every run would triple the byte count; emitting nothing would leak bold red into the next line. So the engine carries _term_style across runs and across frames, and emits only the delta.

blank ≠ skippable

The tempting optimisation “don't write spaces” corrupts the screen the moment you erase text. The rule that works: skip EMPTY, never skip BLANK — and collapse a run that reaches the right edge into CLEAR_TO_EOL, which is both correct and shorter.

tearing

Writing a frame cell by cell lets the user see it arrive. termrender batches the whole frame into one write(), optionally wrapped in DEC 2026 synchronised-output markers so the emulator presents the frame atomically.

resize

SIGWINCH arrives at any moment, including mid-frame. The handler only sets a flag and records the new size; the buffers are resized (and the front buffer invalidated, forcing a full repaint) at the top of the next draw, never from the signal handler.

input ambiguity

A terminal sends ESC for both “the escape key” and “the start of a sequence”, with no delimiter. The parser reads what is buffered, then waits esc_timeout (20 ms) before deciding. Same trick for CSI 1;2 R (shift+F3) vs a cursor position report — the leading 1 disambiguates.

giving the terminal back

Alt screen, raw mode, mouse tracking, bracketed paste, cursor shape, window title, application keys — each one is a mode you must switch off again, including after an exception or a SIGTERM. stop() is registered with atexit and reverses exactly what start() did.

Numbers, and where they come from

Measured on this machine (Python 3.13, pure Python, no C extension): the cost of a frame is proportional to what changed, which is the whole point of the diff.

Where the speed comes from

  • Interned cells — the diff loop compares object identity, not twelve style fields.
  • Identity-keyed cell cache — hashing a Style means hashing four Colours; keying the cache by id(style) instead removes that from the hot path (the cached Cell keeps the Style alive, so the id can never be recycled).
  • normalize_style fast path — a Style instance is already normalised by __post_init__, so the hottest call in the library returns immediately instead of allocating a merge.
  • Run coalescing — neighbouring cells with equal style become one escape sequence.
  • CLEAR_TO_EOL — a run that reaches the row edge with trailing blanks becomes 4 bytes.
  • Lazy bake — layers re-bake their objects only when dirty.
  • Row slice copies — compositing and blitting assign whole row slices, not cell loops.
Measured while building tred: the same editor frame cost 11 ms before the cell-cache and normalize_style changes and 2.5 ms after — a 4.4× speed-up from two small edits in the library, with all 368 existing tests still passing.

10 — input

Keys, mouse, paste, resize

Input is a single undifferentiated byte stream, and it is the messiest part of terminal programming. Parser turns bytes into five typed events; Keyboard handles raw mode and degrades to a no-op when stdin is not a tty (which is why this library works in CI, under pipes, and while generating a web page).

from termrender.input import Parser
 
p = Parser()
p.feed_bytes(b"\x1b[1;6C")     # [Key('ctrl+shift+right')]
p.feed_bytes(b"\x1b[<32;12;6M") # [MouseEvent(drag, left, 11, 5)]
p.feed_bytes(b"\x1b[200~hi\x1b[201~")   # [PasteEvent('hi')]
p.feed_bytes(b" ")              # [Key('space', ' ')]  — bindable, not " "

Key names are stable strings

Every key has a canonical name and modifier flags, and str(key) renders the binding form. tred builds its whole keymap out of those strings:

byteseventbinding string
aKey('a', 'a')a
0x01Key('ctrl-a', ctrl=True)ctrl+a
ESC [ 1;2 AKey('up', shift=True)shift+up
ESC [ 1;6 CKey('right', ctrl=True, shift=True)ctrl+shift+right

Two ambiguities resolved in the parser: a lone ESC waits 20 ms before it may mean “the escape key”, and CSI 1;2 R is shift+F3 rather than a cursor position report because of the leading 1. Both were real bugs found while building tred's keymap — shift+F3 (find previous) silently did nothing until the CPR check learned to look at the params.

Widget ids are position-scoped: calling the same widget at the same coordinates again updates it in place instead of stacking a duplicate. Call it somewhere else and you get a second one. That is what makes a redraw loop idempotent — you never have to erase first.

each CJK character occupies two cells; the right half is a sentinel, so a partial overwrite can be repaired instead of leaving garbage
The one rule to remember: erase() clears raw cells, remove() removes objects. They are the two drawing models and they do not cross over — an object is baked on top of the raw paint during compositing, so erasing the cells underneath it changes nothing.

5 · A 30-line app with the loop

from termrender import App
 
app = App(width=60, height=12, mouse=True)
state = {"x": 4, "y": 3, "dx": 1, "ball": None}
 
@app.on_start
def build(screen):
    state["ball"] = screen.put(state["x"], state["y"], "●", fg="#4ec9b0", id="ball")
    screen.put(2, 10, "space = pause · q = quit", dim=True)
 
@app.on_tick
def tick(dt, screen):
    state["x"] += state["dx"]
    if not 2 <= state["x"] < 56:
        state["dx"] *= -1
    state["ball"].move(state["x"], state["y"])   # one object, no repaint of the rest
 
@app.on_key("space")
def pause(key, screen):
    screen.put(2, 0, "PAUSED", fg="#e3b341", id="flag")
 
@app.on_key("q", "ctrl-c")
def quit_(key, screen):
    app.stop()
 
app.run(fps=30)

What the engine had to provide

paint_runs()

An editor repaints its whole viewport every frame, so object handles are pure overhead. Raw styled runs — added to Layer and Screen for this — draw a line of mixed-colour text in one call.

OSC 52 clipboard

ansi.clipboard() and screen.copy_to_clipboard(), so ctrl+c inside the editor reaches the system clipboard through the terminal.

cell-cache keying

Keying the interned-cell cache by id(style) instead of by value took a hashed tuple of four Colours off the hottest path.

normalize_style fast path

Returning an already-normalised Style unchanged removed an allocation and a dataclass merge from every single run of every frame.

Result: the same editor frame cost 11 ms before those two library changes and 2.5 ms after — with all 368 pre-existing tests still passing. Editing a 969-line Python file now costs about a fifth of a 60 fps budget.

15 — appendix

Sixteen bugs, and what they taught

Sixteen bugs found while building this — most of them silent, which is the dangerous kind. Five came from writing tred against the library, which is the best argument for building something real on top of your abstraction; the last one came from writing this page, when the captured frames came out squashed and the reason turned out to be in Buffer.ansi().
